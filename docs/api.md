# API contract

The Web App exposes `doPost` for normal actions and a closed, read-only `doGet` registry for appointment-link previews. Requests use a JSON envelope containing `action`, `requestId`, `payload`, and, for protected actions, `sessionToken`.

A successful response contains `success`, `message`, `data`, and `requestId`. Every successful protected response also contains a top-level `sessionExpiresAt` ISO timestamp. The browser uses that server-issued value as its sliding idle-expiry hint; every protected action, including reads, counts as activity. The backend bounds durable `Sessions` writes with `SESSION_TOUCH_INTERVAL_MINUTES`, rechecks a due touch under lock, and caps the returned deadline by persisted `ExpiresAt`.

Failures contain a safe `errorCode` and optional field errors. A throttled login uses `LOGIN_THROTTLED`, the same generic login message used for invalid credentials, and safe top-level `retryAfterSeconds` metadata. Unknown or inactive identities execute a dummy bounded-work HMAC verification path, and their bounded throttle cannot lock known active users. The API does not return stack traces, raw PINs, token hashes, or throttle counters.

Protected staff actions include logout, dashboard, order creation/edit/cancel/detail/history, and master data; `LOGIN` is public. `GET_ORDER_DETAIL` returns the authorized editable `RequesterPhone`, while bounded list summaries remain non-PHI. Admin-only actions include cross-department listing, received-item updates, versioned/idempotent `DECIDE_CANCELLATION`, sending/resending mail, and read-only `GET_DATABASE_HEALTH`. `DECIDE_CANCELLATION` accepts `OrderID`, `expectedVersion`, `decision` (`APPROVE` or `REJECT`), and optional bounded `decisionReason`. Approval terminalizes the order/items; rejection restores only the exact persisted pre-request states and eligible cancellation-owned live tokens. New `CANCEL_ORDER` and `DECIDE_CANCELLATION` records bind each request ID to a SHA-256 fingerprint of the normalized payload and reject reuse with a changed reason, decision, or expected version. Legacy successful rows without a fingerprint replay only their stored result.

Create, update, and cancel responses represent the committed business mutation. Their post-commit email work is tracked as a deterministic durable job in existing `RequestLog`/`EmailLog` records. Initial attempt/snapshot reservation is serialized, but mail delivery remains outside locks. Preparation, delivery, finalization, or finalizer lookup failure cannot turn a committed mutation into an API failure. Terminal `EmailLog` and `RequestLog` outcomes are monotonic under stale workers, and definitive delivery evidence may upgrade an earlier uncertain request result; replay reconciles a pending job without duplicating a delivery.

Schema repair is deliberately not an HTTP API action: use the explicit Apps Script editor `setupApplication()` / `initializeDatabase()` path, the scheduled schema check, or the disposable test harness. Public appointment actions use opaque, single-use tokens; they do not trust a caller-supplied role, department, staff identity, or requester email.

The browser sends POST bodies as `text/plain;charset=utf-8` and follows the Apps Script redirect. This deliberately avoids an unnecessary preflight in common browsers. It does not turn Apps Script into a conventional API server: Apps Script controls response headers and redirects, so arbitrary CORS headers cannot be set or relied on. CORS/origin signals are defense in depth; authorization and session checks remain the security boundary.

Do not put patient data, session tokens, raw PINs, Spreadsheet IDs, or secrets in URLs. Appointment URLs carry only an opaque action token and request ID and must be treated as sensitive links.
